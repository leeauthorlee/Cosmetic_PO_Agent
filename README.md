# Cosmetic_PO_Agent

화장품 회사 구매담당자를 위한 **SIL 구매 업무 어시스턴트**입니다. 담당자가 자연어로 질문하면 판매량과 재고 주문량을 확인하고, 표·그래프·CSV로 결과를 활용할 수 있는 Streamlit 챗봇입니다. PO는 Purchase Order(발주)를 뜻합니다.

최종 목표는 **광고비와 프로모션 계획을 반영한 향후 4주 판매량 예측을 바탕으로, 창고별 재고 소진과 발주 필요 여부를 판단하도록 돕는 것**입니다. 현재는 질문 분류, 에이전트 도구 호출, 국내 재고 계산, 결과 표시를 연결한 프로토타입입니다. 판매량 도구는 학습 모델 대신 고정 예시값을 반환합니다.

## 1. 프로젝트 배경과 사용자

기획서의 프로젝트명은 **구매를 최적화하는 챗봇 구축**, 과제 유형은 **기업과제 1 — 채널 운영 코파일럿**입니다. 주요 사용자는 코딩이나 데이터 분석에 익숙하지 않으며 매주 제품별 발주 내역을 결정하는 화장품 회사 구매 팀장입니다.

광고비와 프로모션에 따라 수요가 달라지면 재고 부족 또는 과잉 재고가 발생할 수 있습니다. 이 프로젝트는 담당자가 여러 판매 채널의 데이터를 직접 분석하는 부담을 줄이고, 예측 결과와 재고 정보를 함께 확인하여 구매 계획을 세우도록 지원합니다.

대표적인 업무 질문은 다음과 같습니다.

- 다음 4주 동안 제품이 판매 사이트별로 얼마나 팔릴까?
- 광고비를 변경하면 예상 판매량은 어떻게 달라질까?
- 현재 재고는 언제 소진되며 추가 발주가 필요한가?
- 국내 창고와 아마존 창고에 필요한 물량은 각각 얼마인가?

예측 대상은 매출액이 아닌 **판매 수량(`units`, 단위: 개)**입니다. 위 질문 중 4주 예측, 광고비 시나리오에 따른 실제 수량 변화, 재고 소진 시점, 국외 주문량 계산은 최종 목표이며 현재 모두 구현된 기능은 아닙니다.

## 2. 현재 구현된 기능

| 기능 | 현재 `app.py`의 동작 |
| --- | --- |
| 질문 입력과 대화 | 하단 고정 채팅 입력창으로 질문을 받고 세션의 대화 기록을 표시합니다. |
| 업무 질문 분류 | 경량 LLM이 판매·재고·주문 관련 질문인지 판단하고, 무관한 질문은 안내 후 종료합니다. |
| 판매량 도구 호출 | 제품·광고비·프로모션·채널 등의 인자를 받지만, 실제 추론 없이 1~3주 판매량이 10개라는 고정 문장을 반환합니다. |
| 판매량 표·그래프 | 반환 문장을 각 주차 10개로 표시하고, SKU·판매 사이트별 표와 막대그래프를 제공합니다. |
| 판매 사이트 필터 | 🏪 영역에서 전체·Amazon US·쿠팡·네이버·자사몰 중 선택합니다. 조회된 결과만 필터링하며 추가 예측을 실행하지 않습니다. |
| 국내 주문량 계산 | SKU의 국내 창고 현재 재고와 전달받은 3주 예상 판매량을 비교하여 부족량과 주문량을 계산합니다. |
| 국내·국외 필터 | 🌐 영역에서 지역을 선택합니다. 현재 도구는 국내 창고만 조회하므로 국외 선택 시 결과 없음으로 표시합니다. |
| 주문 보고서 | 사이드바에서 최근 질문의 주문 결과를 팝업으로 확인합니다. |
| CSV 저장 | 현재 표에 표시된 주문 내역을 `sil_inventory_order.csv`로 내려받습니다. 인코딩은 `utf-8-sig`입니다. |
| 브랜드 UI | SIL 로고, 피치 포인트, 크림 배경, 카드형 결과 영역과 업무 가이드를 적용했습니다. |

CSV에는 SKU, 지역, 창고, 예상 판매량, 부족 수량, 주문량이 포함됩니다. 다운로드는 결과 저장 기능이며 **실제 발주를 실행하지 않습니다.**

## 3. 에이전트와 데이터 처리 흐름

```text
사용자 질문
    ↓
send_message: 질문 저장 및 agent.invoke 실행
    ↓
check_order_question: 업무 관련성 분류
    ├─ 무관한 질문 → 안내 메시지 후 종료
    └─ 관련 질문 → 메인 에이전트
                      ├─ 판매량 질문 → predict_sales
                      └─ 주문량 질문 → predict_sales → check_inventory
    ↓
최종 답변 및 도구 반환 메시지 저장
    ↓
extract_display_results: 이번 질문의 결과를 화면용 행으로 변환
    ↓
render_results: 표·그래프·필터·CSV 출력
```

도구 호출 순서는 에이전트의 시스템 프롬프트로 안내하며, 실제 호출 인자는 LLM이 구성합니다. 정보가 없으면 판매량 도구의 기본값을 사용하도록 설정되어 있습니다.

| 구성 요소 | 역할 |
| --- | --- |
| `gpt-5.4-mini` | 현재 코드에 설정된 메인 에이전트 모델 |
| `gpt-5.4-nano` | 현재 코드에 설정된 질문 분류 모델 |
| `QuestionFilter` | 질문 관련성 여부를 담는 Pydantic 구조 |
| `predict_sales` | 판매량 예측 도구 인터페이스와 현재의 고정 예시 응답 |
| `load_inventory_data` | 재고 CSV와 제품 정보를 SKU로 결합하고 캐시 |
| `find_inventory_data` | 해당 SKU의 `KR_WH` 재고 조회 |
| `calculate_order_quantity` | 3주 예상 판매량, 부족량, 500개 단위 주문량 계산 |
| `check_inventory` | 재고 조회와 주문량 계산을 연결하는 에이전트 도구 |
| `InMemorySaver`·`thread_id` | 세션별 에이전트 대화 문맥 유지 |
| `extract_display_results` | 도구 호출 ID로 입력 인자와 결과를 연결하고 이번 질문의 결과만 추출 |
| `render_results`·`show_order_report` | 결과 표시 및 주문 보고서 제공 |

현재 주문량 계산식은 다음과 같습니다.

```text
예상 판매량 = 1주차 판매량 + 2주차 판매량 + 3주차 판매량
부족량 = max(0, 예상 판매량 - 국내 창고 현재 재고)
주문량 = ceil(부족량 / 500) × 500
```

500개 단위는 현재 코드에 고정되어 있습니다. 제품 데이터의 최소 주문 수량을 동적으로 읽어 적용하는 방식은 아닙니다. 미입고 발주량, 입고 소요 기간, 안전재고, 국내 채널 수요 자동 합산도 현재 계산에 반영하지 않습니다.

화면 필터는 이미 받은 결과를 다시 보여주는 기능입니다. 다른 판매 사이트의 결과가 없다고 해서 0개로 간주하거나 새 도구 호출을 실행하지 않습니다. 여러 채널 플래그가 동시에 활성화되거나 모두 비활성화되면 판매 사이트는 `채널 구분 불가`로 표시됩니다.

## 4. 데이터 구성과 활용 계획

제공된 브랜드 A의 2세트 데이터는 원본을 **제품 × 판매 채널 × 주** 단위로 정리한 데이터입니다. 데이터셋의 가상 기준일은 **2026-07-26**, 최종 예측 기간은 **2026-07-27~2026-08-23**입니다. 이 날짜는 실제 실행일과 구분합니다.

| 파일 | 행 수 | 역할 | 현재 앱에서 사용 |
| --- | ---: | --- | --- |
| `sales_weekly.csv` | 1,530 | 과거 판매량·광고비·프로모션·품절 정보로 예측 모델 학습 | 미연결 |
| `future_plan_4w.csv` | 80 | 향후 4주의 계획 광고비와 프로모션을 예측 입력으로 사용 | 미연결 |
| `inventory_now.csv` | 10 | 창고별 현재 재고·미입고 발주량·리드타임 확인 | 국내 현재 재고 조회에 사용 |
| `product_master.csv` | 5 | 제품명·원가·가격·최소 주문 수량·리드타임 등 제품 기준 정보 | 제품명 결합에 사용 |
| `submission_template.csv` | 80 | `pred_units` 열에 예측 판매량을 채우는 평가용 제출 양식 | 미연결 |
| `reviews.csv` | 2,507 | 자사·경쟁사 리뷰 분석을 위한 과제 2 데이터 | 현재 프로젝트 핵심 범위 밖 |

최종 예측 대상은 **제품 5개 × 채널 4개 × 4주 = 80개 예측값**입니다. 평가용 `submission_template.csv`는 챗봇이 출력하는 주문 내역 CSV와 목적 및 열 구성이 다릅니다.

프로젝트 폴더의 실행용 CSV와 별도로 제공된 전체 과제 데이터셋을 구분해야 합니다. 전체 데이터셋은 `app.py`가 자동으로 검색하거나 불러오지 않습니다.

### 판매 채널과 창고의 관계

| 창고 | 사용하는 채널 | 목표 재고 계산 방식 |
| --- | --- | --- |
| 국내 창고 `KR_WH` | 자사몰 `own_mall`, 쿠팡 `coupang`, 네이버 `naver` | 세 채널의 예상 판매량을 합산한 뒤 국내 재고와 비교 |
| 아마존 창고 `AMZ_FBA` | Amazon US `amazon_us` | 아마존 예상 판매량을 해당 창고 재고와 비교 |

판매량은 사이트별로 보여주되, 국내 세 채널은 재고를 공유하므로 발주 판단에서는 수요를 합산해야 합니다. 현재 `check_inventory`는 전달받은 주차별 수량만 사용하므로 이 합산을 자동으로 보장하지 않습니다.

## 5. 모델 개발과 평가 목표

데이터셋 README와 기획서에서 제시한 절차는 다음과 같습니다.

1. 주간 판매 데이터를 탐색하고, `stockout_days > 0`인 행은 학습에서 제외합니다. 품절로 줄어든 판매량을 정상 수요로 학습하지 않기 위한 조건입니다.
2. 2026-06-28 이전 데이터로 학습하고 2026-06-29~2026-07-26의 4주를 검증합니다.
3. 최근 4주 평균을 사용하는 기준선과 비교하여 WAPE가 더 낮은지 확인합니다.
4. 최종 시점까지의 학습 가능한 데이터로 다시 학습하고 `future_plan_4w.csv`의 80행을 예측합니다.
5. 제출 양식의 `pred_units`를 채워 평가합니다. 제공 데이터셋에 채점 코드가 있을 때 해당 폴더에서 `python 정답_채점/score.py 제출파일.csv`로 확인합니다.
6. 테스트 질문 10개에서 적절한 도구를 호출하고 결과를 답변하는지 확인합니다.

WAPE는 전체 실제 판매량 대비 절대 예측 오차의 합으로, 값이 낮을수록 좋습니다.

```text
WAPE(%) = Σ|실제 판매량 - 예측 판매량| / Σ실제 판매량 × 100
```

국내 광고비는 KRW, 아마존 광고비는 USD이므로 단위를 처리하거나 채널별 모델을 구분해야 합니다. 같은 주·같은 채널의 광고비는 모든 제품 행에 반복되므로, 이를 제품별 독립 지출처럼 합산하지 않아야 합니다. 아마존 기록은 6주뿐이어서 검증 구간을 제외하면 학습 데이터가 2주만 남습니다. 단순 평균 방식과의 비교가 필요합니다.

현재 앱에는 이 학습·평가 파이프라인이 연결되어 있지 않으며, 기준선 대비 성능 개선이 검증되었다고 볼 수 없습니다.

## 6. 실행 방법

프로젝트 폴더에서 Python 가상환경을 준비하고 의존성을 설치합니다. 다음은 Windows PowerShell 기준 예시입니다. 이미 `.venv`가 있으면 생성 단계는 생략합니다.

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
```

프로젝트 루트의 `.env`에 API 키를 설정합니다. 아래 값은 자리표시자입니다.

```dotenv
OPENAI_API_KEY=your_api_key_here
```

코드에 지정된 모델을 사용할 수 있는 API 환경이 필요합니다. API 키가 들어 있는 `.env`는 공유하거나 커밋하지 않습니다.

실행에 필요한 파일 배치는 다음과 같습니다.

```text
Cosmetic_PO_Agent/
├─ app.py
├─ README.md
├─ requirements.txt
├─ inventory_now.csv
├─ product_master.csv
├─ assets/
│  └─ sil-logo.png
└─ .env
```

```powershell
.\.venv\Scripts\python.exe -m streamlit run app.py
```

재고 파일 경로가 상대 경로이므로 **프로젝트 루트에서 실행**해야 합니다. 로고 파일이 없으면 화면에는 `SIL` 텍스트가 표시됩니다.

질문 예시:

- `A-SRM-100의 Amazon US 예상 판매량을 알려줘.`
- `A-SRM-100의 재고를 확인하고 추가 주문량을 계산해줘.`

첫 질문은 현재 예시 판매량을 확인하는 용도입니다. 두 번째 질문의 재고 계산은 국내 창고 기준입니다. Amazon US를 언급하더라도 국외 창고 주문 계산이 구현되는 것은 아닙니다.

## 7. 현재 한계와 향후 개발 과제

| 항목 | 현재 상태 | 후속 작업 |
| --- | --- | --- |
| 실제 판매량 예측 | 입력 DataFrame을 만들지만 모델을 로드하거나 추론하지 않음 | 학습된 모델과 전처리 연결 |
| 예측 기간 | 1~3주 예시값 및 3주 합산 | 과제 기준인 4주로 통일 |
| 광고비 시나리오 | 입력 인자는 있으나 반환 판매량은 고정 | 변경된 광고비·프로모션을 모델 추론에 반영 |
| 판매량 결과 형식 | 특정 문장을 정규식으로 해석 | SKU·채널·주차·수량을 담은 구조화된 반환값으로 전환 |
| 창고별 계산 | 국내 현재 재고만 조회 | 국내 채널 수요 합산 및 아마존 창고 계산 추가 |
| 재고 소진 시점 | 미계산 | 주차별 재고 흐름과 부족 예상 시점 계산 |
| 발주 정책 | 부족량을 고정 500개 단위로 올림 | 제품별 최소 주문 수량, 리드타임, 안전재고 정책 반영 |
| 데이터 검증 | 미등록 SKU 조회 시 오류 발생 가능 | SKU 존재 여부, 입력값·데이터 누락 검증 |
| 대화 저장 | 세션 및 프로세스 메모리 사용 | 필요 시 영속 저장과 사용자별 접근 제어 설계 |
| 보고서 | 결과 표와 CSV 제공 | 필요 시 질의 조건·판단 근거를 포함한 보고서 확장 |

추가로 확정할 업무 조건은 다음과 같습니다.

- `open_po_qty`는 미입고 발주량이지만 입고 예정일이 없어, 어느 주의 가용 재고에 반영할지 별도 기준이 필요합니다.
- 국내 리드타임은 14일, 아마존은 35일입니다. 4주 예측만으로는 아마존 리드타임 전체를 다룰 수 없어 추가 예측 또는 명시적인 가정이 필요합니다.
- 데이터셋 README는 아마존 재고 보충을 국내 재고 이송으로 해석하며 최소 주문 수량이 적용되지 않는 것으로 추정합니다. 확정된 업무 규칙으로 구현하기 전에 확인해야 합니다.
- 기획서에는 회사 데이터 활용을 위한 RAG 구상이 있으나, 현재 `app.py`에는 검색·벡터 저장소 기반 RAG가 구현되어 있지 않습니다. 현재는 외부 LLM API를 사용하는 구조이며, RAG 자체가 데이터의 외부 전송을 막는 것은 아닙니다.
